## 0. 现在最值得优化的三件事

**第一，把执行环真正转起来（数据飞轮的唯一断点）。** 库内 8 条执行记录全部是 8/9~8/11 的止损/减仓卖出（buy/add 执行 0 条，data/market.db executions），生产实盘信号表 signal_tracking 为 0 行——「建议→真实成交→回报」环至今没有买入侧样本。它卡住的不只是体验：A1-4 滑点校准（等 executions≥20）、真实 vs 纸面胜率对照、2% 双边成本假设的实盘验证全部悬空（references/first-principles-gap.md 断点 1/2；system-evaluation-2026-08-10.md:105 A1-4）。这是优先级最高的一件事，因为它决定整个系统「能不能越用越好」。

**第二，把「接近买点」从散落的事件变成一条可行动的队列。** 2026-08-12 监控事件里 4 条 near_buy 买点接近度 100%（G2 贴纸 / 翡翠细条纹 / 浮生如梦 / 钴蓝禁锢），批量扫描汇总「1 个已到买点 · 31 个接近买点」（data/batch_scan_latest.json），但用户必须自己打开自选页逐个看报告才能行动；钉钉推送是纯文本无链接（pipeline/monitor.py _build_push_text，无内网链接是有意设计），转化率仅 5.2%（D-3，decision-log 2026-08-10）。39 个自选品是「被动盯盘」，缺一个「今天该看谁」的聚合视图——这是零引擎参数、数据全现成（proximity/buy_distance.py 已算好）就能做的最大体验增量。

**第三，把「回放胜率」和「实盘证据」的边界讲清楚，建立信任基础设施。** 系统已经做了大量正确的事：采集时间可见、去簇胜率对照、J-2 三通道、口径审计（M-5/th_boost/A 通道 note），但证据是分散的：replay.html:7 还写着「503 个 buy 信号（K-2 回放 2025-01-01~2026-08-05）」的过时死文本（现为 317 信号 / 365d 窗口 / v2-T4），signal_tracking 0 行却挂在「回放告警已触发」旁边。用户无法快速判断「这个数字可不可信、对应哪个窗口、几个独立事件」。把文案口径单一事实源化 + 实盘样本缺口可视化，是「破除散户魔咒」原则在产品层的落地——否则引擎再准，信任断点会让用户回到凭感觉。

## 1. 用户旅程（6 条主流程）

### 1.1 发现机会（/discover 发现高分品）
- **流程**：打开 /discover → 看 Top10 综合榜 + 贴纸榜 →（可选）🚀 扫描池内高分品（异步轮询）→ 点品名看报告 → 加入自选。
- **摩擦点**：① 榜单基于 DB 复用（KLINE_FRESH_DISCOVER=3，analysis_service.py:49），依赖 18:00 采集节奏，用户看不到「3 天前数据」会误读为实时；2026-08-11 起已加「采集于」小字（decision-log 2026-08-12），缓解但未解决「慢变量也 3 天」的语义。② 贴纸 153 品均分 7.1、综合分 9.4 的贴纸排在最前，但贴纸 buy 被守卫禁入（观察桶，S-2/W-3 结论）——**高分展示与禁 buy 决策之间没有视觉隔离**，用户可能对贴纸产生买入冲动（data/discover_latest.json 品类热力图）。
- **等待时间**：全池扫描异步 1~5 分钟级（DB 复用，比旧 25-40 分钟快），轮询期间页面可读旧榜；行级 ⚡ 刷新约 30-60s（联网重采）。
- **信息缺失**：榜单排序依据是 composite 综合分（估值折价/TH 反向/动作加分/数据质量），用户看不到「为什么第 1 名是它」；proximity（距买点）不在榜单主列。
- **信任断点**：高分 ≠ 可买（贴纸禁 buy、守卫1 大盘走弱会拦），榜单无「决策口径」标注。

### 1.2 单品分析（/search + 报告弹窗）
- **流程**：输入名称（中文优先）→ 30-60s 分析 → 报告弹窗：决策条（buy/watch/avoid + 市场状态 + 回测 14d 期望条 + 距买点）→ 六维折叠详情（D-1 已分层）→「💼 按建议记录执行」。
- **摩擦点**：① 冷分析 30-60s（Playwright 采集，search.html:31 明示「预计 30-50 秒」）；已缓解：B-4 当日 6h 复用 + 报告 6h 缓存 + 大盘 5min 缓存（decision-log 2026-08-12，冷重建 2.9s → 缓存命中 3-21ms），但 /search 冷品仍要等。② 报告「回测 14d 71%」是 365d 回放口径，未与「当前 market regime」解释关联（低波/洗盘/恐慌不同 regime 期望不同，j2_channel_status.json 2025-11/12 月 14d 仅 64.3%/54.5%）。
- **信息缺失**：期望条只给 win14/avg30 与 n/事件数（J-1 已带独立事件数），不给窗口与月度分解；bid_highest/spread（求购断层）已落 snapshots 但按 F-2 计划不展示。
- **信任断点**：回放 317 信号 vs 生产实盘 0 样本之间无桥；kline_stale_days 兜底条已提示数据旧，但「旧数据下的 buy 建议」与「新鲜数据下的 buy 建议」没有置信差异表达。

### 1.3 建仓决策（报告决策条 → 是否买）
- **流程**：读决策条 action/action_detail → 期望条 → 距买点 proximity → 仓位提示（首仓 ≤10% · 单票敞口 ≤30%）→ 执行或放弃。
- **摩擦点**：① buy 信号少且依赖大盘环境（守卫1 大盘走弱冻结、I-13 深值仅企稳段、T4 chg8 追高禁买），用户多数时候看到的是 watch/avoid——**「为什么现在不是买点、还差什么」需要自己从 gaps 里拼**（proximity.gaps 已有，但只在报告内）。② 持仓品报告重建 ~1.4s（保留补仓/止损卡片，decision-log 2026-08-12），可接受。
- **信任断点**：分级仓位（panic 族 0.30 / 基础 0.12-0.30）是回测参数，报告只显示百分比，不显示「为什么这个仓位」（族级归因 portfolio_attribution.json 未接入报告）。

### 1.4 批量扫描 / 监控（/watchlist + 钉钉推送）
- **流程**：批量扫描（3h 复用，analysis_service.py:48）→ HTML 汇总面板（综合分降序）→ 行级 ⚡ 刷新 → 点品名看报告；同时 monitor 每日 12:00/21:30 推送 8 类事件。
- **摩擦点**：① 推送 37~51 条事件/天（settings monitor_push_2026-08-10_night 37 条 / 08-11 51 条），文本明细截断 10 条，near_buy 与 price_spike 混排，噪音大 → 转化 5.2%。② 推送无链接无动作（有意设计），用户必须回 Web 端。③ 批量扫描结果按综合分排序，不是按「距买点」排序——扫描面板与决策动作（该不该执行）脱节。
- **信息缺失**：market_regime 只在批量扫描环境条/报告徽章，推送标题带 bucket（monitor.py title），但「今天大盘状态下该不该开新仓」无一行结论。

### 1.5 执行录入（exec-modal，F-1）
- **流程**：报告/批量扫描「💼 按建议记录执行」→ 弹窗预填名称/动作/建议价/信号 → 手填成交价与数量 → 确认 → 同步持仓。
- **摩擦点**：① 成交价必须 >0 才可提交，留空走参考价二次确认（exec_modal.html submitExec 兜底），多一步。② 买入侧入口存在但**实际使用为 0**：8 条执行全为 sell/reduce（data/market.db executions）——用户不录入买入，可能因为「买在外面平台，懒得记」或「buy 信号太少」。③ 录入后没有「这笔该不该买」的事后反馈（执行复盘对照卡在 watchlist 深处，无样本时几乎不可见）。
- **信任断点**：滑点统计依赖 advice_price（A1-4 已清 3 条失准记录，样本 8→5，decision-log 2026-08-12）；用户对「按建议执行到底赚不赚」无体感。

### 1.6 复盘迭代（/replay + /checkup + 执行复盘）
- **流程**：/replay 看 317 信号 14/21/30d 表现（meta 数据驱动，但页头静态文案过时）→ /checkup 看 J-2 三通道 + C 通道月度判定 → watchlist 执行复盘对照卡。
- **摩擦点**：① replay.html:7 静态文案「503 个 buy 信号（K-2 回放 2025-01-01~2026-08-05）」与当前 317 信号 / 365d 窗口（2025-08-10 起，benchmark_compare.json replay）冲突——**死文本漂移的教科书案例**（与 J-2 A 通道 note 同类，decision-log 2026-08-12「A 通道计数口径核对」）。② /checkup 生产实盘「暂无已回填样本（0 条）」（checkup.html），而 C 通道状态是「已触发（回放口径信息级告警）」——**两种口径并排展示，无一行说明「回放告警 ≠ 实盘劣化」**。③ 复盘信息分散三页，没有「回放 → 实盘 → 我的执行」三层对照总览。
- **信息缺失**：信号复盘无「当月胜率 vs 全年」的月度分解入口（数据在 j2_channel_status.json C.monthly，checkup 有表，replay 没有）；执行复盘无样本时空白卡（exec-review-card 显示但内容空）。

## 2. 痛点清单（P0 / P1 / P2）

> 分级口径：P0 = 阻碍核心决策闭环（数据飞轮/信任底座）；P1 = 体验明显受损；P2 = 锦上添花。
> 每条含：现象 → 影响 → 根因 → 建议 → 改动边界（展示层/数据层/引擎层）→ 预估工作量；并标注「产品体验线」或「策略/数据能力线」。本清单**不含任何引擎参数/信号规则改动**；凡涉及展示口径的建议，落地时按纪律同步 decision-log.md。

### P0

#### P0-1 执行环无买入侧样本，飞轮未转（数据线/体验线）
- **现象**：executions 8 条全为 8/9~8/11 的 sell/reduce（止损/减仓），buy/add 0 条；signal_tracking 0 行；监控 new_buy_signal 事件从未出现。
- **影响**：A1-4 滑点校准（等 executions≥20）、真实 vs 纸面胜率、2% 成本假设实盘验证全部悬空；「按建议做到底赚不赚」无法回答（first-principles-gap.md 断点 2）。
- **根因**：① 买入侧信号稀缺且大盘弱（守卫1/I-13/T4 抑制 buy，j2_channel_status.json 大盘「阴跌中继区」）；② 用户买入多在外部平台成交后不录入，录入入口（F-1）存在但无「录入动机」；③ 买入执行后无即时正反馈（无净值曲线、无对照）。
- **建议**：① 报告/批量扫描 buy 行加「✅ 已记录执行」持久状态 + 7 天未记录提醒（E-2「建议未执行」标记已有基础，扩展为列表）；② 执行弹窗「成交价」预填当前锚价并允许一键确认（去掉二次确认摩擦，仍保留可编辑）；③ watchlist 新增「我的执行」汇总入口（当前藏在页面深处，watchlist.html:186 起）。
- **改动边界**：展示层 + 数据层（写入仍走现有 executions API）；不碰引擎。
- **预估**：3-4 天（含测试）。

#### P0-2 生产 buy 信号记录链路未挂全 / 疑似断链（数据线）
- **现象**：signal_tracking 0 行，而 2026-08-12 批量扫描汇总「1 个已到买点」（data/batch_scan_latest.json）；record_buy_signal 仅在 pipeline/scan_tasks.py:187 被调用（批量扫描路径），单品分析 analyze_fresh 未挂接（webapp/analysis_service.py:14 仅 import），pipeline/monitor.py:187 docstring 却写「analyze_fresh/批量扫描落库」——**文档与代码不符**。
- **影响**：J-2 C 通道「生产实盘判定」永远积累不起来；/checkup 长期显示「0 条」会把「链路 bug」误读为「市场没给信号」。
- **根因**：2026-08-07 C 通道落地时只接了批量扫描路径，单品/自选/搜索路径遗漏；docstring 表述超前。
- **建议**：① 核验批量扫描 buy 是否真实落库（现 0 行，需排查 record 分支的 action 判定或 DB 事务）；② analyze_fresh 统一出口补 record_buy_signal（analysis_service.py:504），与批量扫描同口径（entry=当日 chart close，net 扣 2%）；③ docstring/文档对齐；④ 加 t_signal_tracking 冒烟校验（记录→回填链路可测）。
- **改动边界**：数据层（新增监测记录，不改信号）；属监测口径变更，按纪律同步 decision-log.md。
- **预估**：1-2 天（先核验，再补挂）。

#### P0-3 推送→决策→执行的动作断层（体验线）
- **现象**：8/12 监控事件 4 条 near_buy 100%（data/market.db monitor_events），推送为纯文本无链接（monitor.py _build_push_text 注释「纯文字自包含、无内网链接」），用户看到「买点接近度 100%」后必须开电脑回 Web 端找品。
- **影响**：动作转化率 5.2%（D-3，样本不足仅参考）；高价值信息（buy 前哨）被浪费在只读文本里。
- **根因**：① 安全上刻意不加内网链接（合理）；② F-7「钉钉卡片一键执行」因资金安全设计待议，卡在 P2。
- **建议**：近 2 周先做**轻量版**：推送正文加「品名 + 当前价 + 建议动作」可复制一行（已有 detail），再在 web 端 /watchlist 加「📌 今日关注」卡片（从当日 near_buy/stop_loss 事件生成，一键打开报告）；完整版钉钉 action 卡片（二次确认 + 幂等）留 F-7。
- **改动边界**：展示层（监控事件消费端）；不碰监控事件生成规则（阈值在 monitor.py 为提醒层参数，本次不动）。
- **预估**：2-3 天。

### P1

#### P1-1 冷分析 30-60s 等待体验（体验线）
- **现象**：/search 冷品分析 30-60s（search.html:31 明示「预计 30-50 秒」），弹窗只有转圈。
- **影响**：用户在中途流失；高频使用者的单次分析成本高。
- **根因**：Playwright 全链路采集（csQAQ 限流敏感，G-4 退避 1.5s）；B-4/6h 缓存已大幅缓解热路径（缓存命中 3-21ms）。
- **建议**：① 分析中模态升级为「步骤进度」（搜索→详情→K线→在售量→评分），让等待可预期；② 失败/超时兜底提示已有（kline_stale），补「可强制联网重试」按钮文案。
- **改动边界**：展示层；不影响引擎口径。
- **预估**：1 天。

#### P1-2 死文本口径漂移（replay 页 503 vs 317）（体验线/信任线）
- **现象**：replay.html:7 静态文案「新版引擎 503 个 buy 信号（K-2 回放 2025-01-01~2026-08-05）」；当前回放产物为 317 信号 / 365d 窗口（2025-08-10 起，data/benchmark_compare.json replay.signals=317）。
- **影响**：用户看到的样本数/窗口与实际数据不符，信任受损；与 J-2 A 通道 note 死文本（decision-log 2026-08-12）同类问题复发。
- **根因**：页头文案硬编码，未随回放基线（581→503→332→317）同步；/api/signals/replay 的 meta（count/range/generated）是数据驱动的，但模板没用它。
- **建议**：replay 页头改由 d.meta 注入（窗口/信号数/引擎版本）+ 全仓 rg 扫「503|370|332|2025-01-01」等硬编码口径文案（decision-log 2026-08-12「主引擎口径审计」已做代码侧，展示文案侧补一轮）；可加 t_replay_page_copy 冒烟校验。
- **改动边界**：展示层；展示口径改动，同步 decision-log.md 一行。
- **预估**：0.5-1 天。

#### P1-3 贴纸高分与「禁 buy」决策无视觉隔离（体验线）
- **现象**：discover 品类热力图印花 153 品均分 7.1、综合 9.4 的贴纸居首（data/discover_latest.json）；贴纸 buy 被观察桶守卫（S-2 证伪、W-3 未达 A2，decision-log 2026-08-12）。
- **影响**：用户可能对「高分贴纸」产生买入冲动，而引擎根本不支持贴纸 buy；「发现高分」页成为误导入口。
- **根因**：综合分对贴纸照常计算（composite_score 通用），但决策层对贴纸禁 buy；两榜共用一张榜单渲染，无「观察桶」标签。
- **建议**：贴纸行/榜加「🧪 观察桶 · 未进 buy」徽章 + 综合榜顶部一行说明「贴纸仅供研究，买点需 A2 验证」；保持贴纸独立榜（已有双榜刷新）。
- **改动边界**：展示层；展示口径变更（标注语义），同步 decision-log.md。
- **预估**：0.5 天。

#### P1-4 推送噪音大，near_buy 与止损混排（体验线）
- **现象**：单次推送 37-51 条事件（settings monitor_push_*），明细截断 10 条；near_buy（warn）与 stop_loss（danger）、price_spike 混排。
- **影响**：高价值事件（新 buy / 持仓破位）被噪音淹没；转化率 5.2%。
- **根因**：推送=所有 warn+danger 明细（monitor.py _build_push_text），无用户偏好分层。
- **建议**：① 持仓品的 danger 事件永远置顶；② near_buy 降为「仅计数 + Top3 品名」（阈值/规则不动，仅消费端分层）；③ 后续做订阅偏好（settings 表已具备 KV 能力）。
- **改动边界**：展示层（推送文本组装）；不改 monitor 事件生成阈值（提醒层参数本次不动，若要动需单独评审）。
- **预估**：1 天。

## 5. 北极星与指标

### 北极星：连续 30 天有新增执行记录（含买入/补仓）
- **为什么**：四环价值链（first-principles-gap.md）唯一未转的环是执行；买侧 0 样本直接卡住 A1-4（滑点校准）、真实 vs 纸面对照、2% 成本验证。执行环一旦日常化，其余指标（胜率、滑点、净值）自然可算。
- **可衡量**：executions.created_at 每日新增去重；目标与 first-principles-gap.md 衡量标准 1 对齐（30 天 + 结算率 ≥90%）。

### 过程指标（3-5 个）
1. **买入执行占比**（buy/add 执行 ÷ 总执行）：当前 0/8。检验「建议→建仓」链路是否真的被信任；过低则说明 buy 信号可信度或录入动机有问题。
2. **生产 buy 信号回填率**（signal_tracking filled14 ÷ 到期信号）：当前 0/0（先修 P0-2 链路）。C 通道实盘判定的前提。
3. **推送→报告转化**（push_id → 报告点击，D-3 已有归因框架）：当前 5.2%（样本不足）；P0-3 落地后应显著上升。
4. **报告页新鲜度命中率**（复用窗口内直接出报告的比例）：体现「数据时效可见性 + 复用策略」的健康度（decision-log 2026-08-11 学到的「时效可见性是复用策略的必要配套」）。
5. **买点队列使用率**（队列页/卡片打开 → 报告打开 → 执行录入 的漏斗）：验证 P0-3/第 7 节方案是否真正缩短决策路径。

## 7. PM 视角最有价值但尚未立项的 1 个功能：买点队列（Buy Watch Queue）

### 7.1 一句话
把 39 个自选品从「被动列表」变成「今天该盯谁」的行动队列：按距买点（proximity）聚合 + 当日监控事件徽章 + 一键打开报告/记录执行，全部数据现成、零引擎参数。

### 7.2 用户价值
- **决策闭环**：填补「monitor 只读提醒 → 用户开 Web 找品」的断层（P0-3）；买点接近度 100% 的品（8/12 有 4 条）当天即可被看到并行动。
- **注意力聚焦**：批量扫描 38/39 成功、其中 31 个接近买点（batch_scan_latest.json），队列把「31 个都接近」压缩为「按接近度排序 + 事件徽章」的一屏。
- **信任增强**：每行带采集时间（复用现有 collected_at 链路）与最近决策（watch/buy），用户能看出「数据是几点采的、引擎最近一次怎么判」。

### 7.3 数据依赖（全部现成）
- snapshots / analysis_results：最近一次 fusion_decision 与 proximity 分（buy_distance.py 已产出）。
- monitor_events：当日 near_buy / stop_loss / price_spike 事件（monitor.py 已生成，301 条积累中）。
- price_history：最新价 + 采集时间（collected_at，2026-08-11/12 已全链路透传）。
- signal_tracking（P0-2 修复后）：当日 buy 信号置顶。
- 批量扫描 3h 复用窗口 + 报告 6h 缓存：队列点击报告 <100ms（2026-08-12 缓存优化后）。

### 7.4 实现边界
- **展示层 + 轻量聚合服务**：新 API GET /api/watchlist/buy-queue（只读 DB 聚合：自选品按 proximity 降序、按当日事件打徽章、buy 信号置顶、7 天去重口径复用引擎现有规则）+ watchlist 顶部「📌 今日关注」卡片（或独立 tab）；不新增采集、不产生信号、不改任何引擎输出。
- **口径红线**：队列只**聚合展示** fusion_decision 与 proximity 输出；proximity 非买入概率的提示（analysis.html 已有）必须在队列页保留；**不做**「队列 → 自动 buy 接线」（那属于新信号族，须 A2 walk-forward + 聚类 + 置换，三件套）。
- **展示口径变更**：队列引入「距买点」为排序主口径，与批量扫描（综合分排序）并列，需在 decision-log.md 记一行展示口径说明。

### 7.5 风险
- **R1 数据新鲜度误读**：复用窗口（3h）内队列数据可能滞后 → 每行必须带采集时间（现有链路直接复用），与 2026-08-11「时效可见性」结论一致。
- **R2 队列变成新的「信仰面板」**：聚合视图放大了「接近买点」的存在感，用户可能不等引擎 buy 就手动入场 → 队列页顶部固定一行「接近买点 ≠ 买点，以报告决策条为准」；建议后续做「队列触发 → 引擎判定」的显式动作对照（研究项，非本方案）。
- **R3 事件噪音**：near_buy 每日多条会稀释注意力 → 徽章仅显示当日最新一条 + 计数，结合 P1-4 推送降噪。
- **R4 与现有页面的重复**：批量扫描已按综合分排序 → 队列定位为「自选专属、动作导向」，与扫描（池内/批量）错位；若不重复，可退化为 dashboard 卡片而非独立页。
- **R5 依赖 P0-2**：若 buy 信号记录链路不修复，队列中「新 buy 信号」徽章恒空——排期上 P0-2 必须先于或并行于本功能。

### 7.6 排期与验收
- 排期：v0（dashboard 卡片 + API）2-3 天；v1（独立队列页 + 事件档案链接）+2 天；与 P0-3「今日关注」卡片共用实现。
- 验收：① 队列按 proximity 排序与批量扫描/报告口径一致（t_buy_queue 冒烟）；② 点击行 → 报告缓存命中 <100ms；③ 每行显示采集时间；④ buy 信号行置顶且带「引擎判定」徽章；⑤ 不产生任何新信号/参数（git diff 仅 webapp/pipeline 展示层）。
