- 开箱量水平与大盘水平同窗口相关 +0.64（共享趋势伪相关）；开箱量日变化 vs 当日大盘收益 r=-0.17、vs 次日 r≈0、vs 未来 3 日 r=-0.24（n=29，不显著）。

**结论（性价比判断）**：
1. 开箱量是**同步/滞后热度指标**（跟随大盘涨跌），未发现对大盘/单品价格的领先预测力——与现有情绪/TH/贪婪指数信息重叠，无边际信息。
2. 历史仅 32 天 + 自选品与活跃箱交集≈0 → **无法回测验证、因子落不到现有标的**。
3. **P2 不投产引擎因子、不建采集模块**（性价比低，符合「研究先行、实施殿后」）；若未来自选覆盖活跃箱产物再验证时，以 stat/case + info/roi 每日快照（2 调用/天，约 30 分钟工作量）补采积累。
4. 学到的新思路：① 数据可用性必须实测确认（「763 天可回补」预期被 32 天上限证伪）；② 热度类指标与情绪因子同质，落地前先问「是否提供边际信息」；③ 单 regime（单边下跌）窗口内的事件研究无法分离「开箱突增效应」与「均值回归」，需多 regime 样本。

## 大盘刷新性能修复：get_conn 重复建表 DDL 是根因（2026-08-06，性能优化）

**现象**：大盘板块刷新从 ~1s 级退化到 12.5s，用户反馈与新增功能有关。

**定位（cProfile）**：`/api/market/refresh` 链路 = fetch_market_index(1.5s) + analyze_index_full(2.6s) + _market_snapshot(**11s**)。根因：`db.get_conn()` 每次连接都执行 `_init_schema` 的 32 条 CREATE TABLE DDL（WAL 写竞争下每条 execute 约 0.1s）；新功能把分析链引入刷新路径（TH/融合决策 → `event_risk_coefficient` → 每次开连接；大盘 regime → `_market_snapshot` → `analyze_index` → 同上），一次刷新链上 3 次 get_conn = ~11s。

**修复**：
1. `db.get_conn()` 按 DB 路径缓存 schema 初始化（进程内文件库只跑一次 DDL；`:memory:` 每连接新库不缓存）——`_market_snapshot` 11s → 冷 2.6s / 热 0.01s，全链路 get_conn ~0s。
2. `run_server.py` 启动时预热 schema（首刷不再承担一次性建表成本）。
3. 刷新链路其余成本均为必要网络调用（大盘指数 1.5s + K线 1.7s(1h 缓存) + 贪婪情绪 1.5s(10min 缓存)）。

**效果（实测 HTTP）**：刷新 12.5s → 冷首刷 4.9s（纯网络）/ 热刷 1.5s（8 倍提升）；test_smoke 64/64。

**学到的新思路**：① 连接工厂里跑 DDL 是隐藏的 O(n) 放大点——「每连接建表」在低频脚本里无感，但被分析链多次调用 + WAL 写竞争放大后就是秒级卡顿；② 排查性能先 cProfile 找「每个连接都重复做的事」，而不是先怀疑新增功能本身；③ 启动预热把一次性成本从首个用户请求移走，冷启动体验等价热态。
